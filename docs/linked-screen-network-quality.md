# Linked Screen 弱网流畅度与操作延迟需求

适用对象为 AirPointer Remote 的 Mac 接收端和 iPhone Linked Screen。本文包含实现要求与待真机标定的验收目标。

当前代码已接入 Mac 普通共享的自适应码率与帧率、两端视频诊断日志，以及基于新关键帧确认的输入恢复。分辨率保持最长边 1280，先用真机数据判断是否需要增加 960 档。诊断写入本地统一日志，可按 `LinkedVideo` 和 `LinkedVideoClient` 类别查看。iPhone 收帧间隔包含静止画面产生的间隔，分析时需要对照 Mac 的采集活动。动态尺寸协商、应用内诊断导出和 P3 媒体实验仍待实施。所有档位、时间阈值和验收目标都是初值。独立蓝牙鼠标、Watch 操作和 Lid Desktop 合盖保活沿用各自的生命周期。

## 1. 用户任务与成功条件

用户带着手机从书桌走到隔壁房间，仍希望看清 Mac 弹窗、把指针移到目标、点一次并及时看到结果。系统应在原会话内自动降低传输负载；走回近处后自动恢复清晰度。阅读静态文档优先保字，连续滚动和拖窗优先保画面新鲜度。画面确实落后时，明确显示当前哪些操作可用。恢复后继续使用原触控板、缩放位置和输入草稿。锁屏、权限撤销和显示器消失继续按原安全边界结束或暂停共享。

## 2. 当前实现与诊断假设

| 已核实的工程行为 | 对设计的影响 |
| --- | --- |
| Mac 以 H.264、最长边 1280、目标 30 FPS、普通共享目标 3 Mbps 编码；PiP 已有 1.4 Mbps 与 650 kbps 两档 | 先将已有动态调码率能力用于普通共享。PiP 单独统计、单独调参 |
| 编码串行，待编码样本只保留最新一张；已开始编码、等待回执的帧最多 3 张 | 慢回执会限制吞吐。回执耗时若持续 300 ms，三帧窗口的理想上限约为 10 FPS，盲目扩大窗口会增加陈旧画面 |
| iPhone 将样本送入 renderer 后发 frameAck；暂停时也可能回 ACK 以排空管道 | ACK 可估算发送到入队的耗时。显示耗时需要另测；暂停回执不能用于恢复输入或升档 |
| 已有 600 ms 在途帧保护、超时、拖动释放、前后台恢复与焦点令牌检查 | 扩充 iPhone 的反馈，并保留 Mac 最终校验。静止桌面长时间没有新帧可以是正常现象 |

实现入口：[Mac 采集、队列和输入](../Mac/LinkedScreen/LinkedHost.swift)、[编码器](../Mac/LinkedScreen/LinkedEncoder.swift)、[共享协议](../Shared/LinkedTransport.swift)、[iPhone 收帧](../iPhone/LinkedScreen/LinkedVideoStream.swift)、[会话状态](../iPhone/LinkedScreen/LinkedClient.swift)、[共享界面](../iPhone/LinkedScreen/LinkedScreenView.swift)。

家用局域网要分别看 Mac 到路由器、手机到接入点两段；在手机热点下要看手机与 Mac 之间的无线链路。Mesh 漫游、同频争用和 TCP 重传均可能引起瞬时停顿。Mac 编码变慢、主队列繁忙、手机发热或渲染积压也可能出现相似现象。把这些列作假设，不能用物理距离、Wi-Fi 图标或蓝牙信号强度单独定因。

## 3. P0：建立可复现的基线

- Mac 用单调时钟记录采集回调、开始编码、编码完成、提交发送、ACK 到达；每秒汇总有效采集数、被新样本替换数、编码字节数、窗口占满时间和最老在途帧年龄。实际编码码率按字节数 × 8 ÷ 时间计算。
- iPhone 在视频队列记录连续帧接收间隔、样本准备到入队耗时、renderer 失败或 flush 次数。标记正常播放、后台、PiP 暂停、恢复首帧。对照 Mac 的采集活动，避免把静态空闲记成卡顿。
- 每份结果记录构建号、机型、系统、画面尺寸、网络拓扑、场景与阶段。每秒聚合一次，仅在用户主动导出时提供诊断摘要。禁止写入帧内容、选中文字、草稿、配对密钥或网络名称。
- 分别统计 p50/p95；持续动态场景另记每分钟超过 250 ms 和 600 ms 的停顿次数及最长停顿。分母用有效动态时长。跨设备时间戳不能直接相减。端到端点击反馈用同一台高速相机拍摄手指点击和手机画面响应，或用受控测试页面做同设备可见反馈计时，并标明测量方法。
- 归因顺序：编码耗时升高且回执稳定，先查 Mac；编码稳定、窗口持续占满且回执变慢，先查链路与接收队列；ACK 正常而画面仍卡，查 iPhone 渲染、温控和前台负载；配对也断开时单独检查 BLE 心跳。控制与图传各自记断开原因。

## 4. P1：在原共享会话内自动调码率

| 普通共享档位 | 目标码率 | 初始画面策略 |
| --- | --- | --- |
| 清晰 | 3 Mbps | 最长边 1280，最高 30 FPS |
| 均衡 | 1.8 Mbps | 先保留像素和帧率 |
| 弱网 | 1 Mbps | 先保留像素，按 P2 条件降低实际采集帧率 |

1. 新会话从清晰档开始。在 Mac 所属队列中维护当前代次的样本，每秒评估一次。建议使用最近 2 秒至少 8 个有效 ACK 的 p95。启动关键帧、恢复首帧、切屏、后台和 PiP 的样本从普通窗口剔除。
2. 连续两次评估 ACK p95 超过 150 ms 且窗口占满超过窗口时间的 30%，降一级。动态画面最老在途帧达 350 ms 时，允许无 ACK 紧急降一级；每次降档后至少观察 2 秒。避免单个大关键帧触发多次降档。
3. 连续 10 秒有足够动态样本、p95 低于 80 ms 且窗口占满低于 10%，升一级。样本不足保持当前档。升档后 3 秒内再次拥塞则退回，并将下一次升档观察延长到 20 秒。
4. 只调整现有 VideoToolbox 会话的平均码率，检查属性设置返回值，成功后再更新状态。记录目标和实测速率。普通模式、PiP、恢复回调共用一个设置入口；切模式清空统计，避免两个策略争写。旧 iPhone 可以直接受益于 Mac 本地策略。
5. 正常适配不弹框。共享选项里显示当前质量；只有影响操作时才在画面上提示。首版默认自动，无需用户在走动时手选网络或反复选屏。

## 5. P2：限制积压，保护点击和文字

- 保留三帧上限和最新待编码样本。最低码率仍连续 4 秒拥塞，先将实际采集上限降至 20 FPS，再观察 4 秒降至 15 FPS。保留 1280 阅读小字。最低帧率仍拥塞时才试最长边 960。通过采集配置或编码前限流改变实际输入频率，同时同步编码器预期帧率。恢复时逐级提升，一次只改一项。
- 改分辨率走串行重配置：冻结依赖画面的输入，立即释放拖动，停止向旧编码器送样本，排空或按代次作废旧数据；发送带新尺寸的配置，重建编码器，发送可独立解码的关键帧；iPhone 确认新代次首帧后放开输入。对旧端未协商动态尺寸时，只调码率与帧率。配置失败回退到最近可用配置，超时则提供 Resume Sharing。
- 已写入 TCP 的陈旧帧无法撤回。编码前可替换样本；已经编码的预测帧不能任意跳过，否则可能破坏后续解码。不得靠重复发送关键帧解堵。
- 最老在途帧达到现有 600 ms 保护线时，Mac 阻止依赖当前画面的点击、滚动、按下、拖动和文字提交，允许停止、释放及已有的无按键相对移动。手机显示 “Video delayed · Clicks paused”，禁用对应按钮。拒绝输入并保持草稿，不缓存点击待恢复后重放。
- 单个旧 ACK 不足以解除拥塞保护。待旧积压清空、收到对应新画面的确认且最老帧年龄回落后解除。没有屏幕变化且无积压时，以心跳维持会话；严禁仅凭最后一帧到达时间禁用静态桌面。完全断网沿用原超时退出并明确提示；切回同一网络时复用现有认证与恢复流程。
- 用户在编辑框输入期间，网络下降只改变画质；焦点令牌、草稿和提交请求 ID 继续生效。已发送但无结果的提交提示检查 Mac，不自动重试。换屏、撤销权限、休眠、进入后台时取消未生效的重配置，释放按键。保持同一显示器的缩放中心及归一化点击映射；换到另一块显示器回全景。

## 6. P3：有数据支持时再变更传输

当 P1/P2 后仍反复出现动态画面停顿，且受控实验显示编码稳定、丢包增加会触发长尾停顿，再立项对照现有 TLS/TCP 与 WebRTC 媒体通道。在相同设备、相同 H.264 画面尺寸和同一弱网配置下比较停顿、点击反馈、功耗和恢复成功率。公网中继不在本次范围。视频会话须绑定已有配对和短期会话凭据，验证媒体端身份；保留可靠有序的控制、释放、文本及去重。双方协商新能力，握手失败回到现有 TLS/TCP。若改善不足或耗电显著增加，保留现有实现。

## 7. 真机矩阵与发布门槛

同一 Mac、同一 iPhone、同一桌面内容，用当前版本作基线。每种组合重复 3 次；滚动、拖窗各 60 秒，点击可变色按钮至少 20 次。记录距离及障碍物，但以实测延迟、吞吐、抖动描述链路条件。

| 必测场景 | 验收观察 |
| --- | --- |
| 同房间和隔墙；Mac Wi-Fi 与 Mac 有线对照；手机热点 | 确认实际路径。相同负载比较编码耗时、ACK、入队间隔与可见反馈；排除 BLE 断开样本后再比较图传 |
| 在传输路径上分别施加 2 Mbps 限速、100 ms 附加往返延迟、1% 丢包，再组合测试 | 单因素实验留下瓶颈证据。降速后自动降档，恢复后逐档升回；检查 ACK 停止时仍能触发保护 |
| 站着读文档 2 分钟，再滑动和缩放；播放快速变化内容 | 静态不误报卡顿，第一下点击生效。中文小字、菜单、光标和滚动内容可辨认；放大后点选位置正确 |
| 拖动中掉线、键盘提交时掉线、Mac 权限撤销 | 松键成功，无粘滞、重复提交或恢复后的延迟点击。草稿可找回，允许手动停止 |
| 隔墙走回、Mesh 切换、热点关闭再开启、后台返回、PiP 来回切换、切换显示器 | 区分短时抖动和真实断连。原连接存续时无需重新选屏；重建会话遵守已有授权。切换模式后第一帧能解码 |
| 老 Mac 搭新 iPhone、新 Mac 搭老 iPhone；低电量或发热；连续操作 20 分钟 | 新增协议字段可缺省，旧端可正常共享；记录 CPU、温控、内存和队列上限，确认无持续增长 |

建议首轮门槛：在可复现且基线每分钟至少 4 次长停顿的弱网条件下，超过 250 ms 的停顿次数较基线减少至少 30%；正常网络点击可见反馈 p95 恶化不超过 20 ms；稳定恢复后在有持续动态样本的 30 秒内回到清晰档；恒定条件下稳定后每分钟最多 2 次切档。误点、卡键、重复插入、串屏和越过权限控制的容忍次数为零。记录每轮原始计数和有效时长，样本不足标记待复测。

## 8. 实施与交付顺序

| 阶段 | 改动与交付 | 放行依据 |
| --- | --- | --- |
| P0 观测 | Mac 与 iPhone 增加聚合指标；留存近远、热点、限速三组基线 | 同一次测试可区分采集、编码、链路和播放问题 |
| P1 自适应 | Mac 编码器返回调参结果；提取可输入合成时间序列的码率决策逻辑 | 验证高延迟、无 ACK、静态、单个尖峰、慢升档和 PiP 切换；与固定 3 Mbps 对照 |
| P2 保护与降级 | 扩展共享协议能力协商、两端积压状态、采集频率和动态尺寸；更新共享页面提示 | 通过真机矩阵；能独立关掉动态尺寸或自适应并回到现有配置 |
| P3 媒体对照 | 独立实验开关与 A/B 结果，记录是否迁移的结论 | 满足 P3 进入条件，并验证新旧版本互通后才合入发布路径 |

现有 Tests/run-linked-checks.sh 和 Tests/run-phone-checks.sh 用作回归底线。新增针对状态机的确定性测试，覆盖旧代次 ACK、采集空闲、持续拥塞、重配置失败、拖动释放和一次性提交。发布报告附设备与版本、网络拓扑、各条件的基线和候选数据、操作异常及回退结果。自动化通过后仍需两端真机走完输入与恢复流程。
